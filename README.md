## 🚀 Selected Work

### 🌿 KAI 2.0 &nbsp;·&nbsp; AI Well-Being Companion
<sub>Role: Product Design + Frontend &nbsp;|&nbsp; Tools: Figma, FigJam, React, TypeScript</sub>

<p align="center">
  <img src="https://github.com/user-attachments/assets/284ea5b3-67cd-46b7-a68c-ce55a34be54b" alt="KAI 2.0 preview" width="100%" />
</p>

| | |
|---|---|
| **🌸 Problem** | Reaching out when you're low is hard, and most wellness apps feel clinical or demanding. |
| **💡 Approach** | Remove every barrier to the first check-in, and keep the tone soft at every state. |
| **✨ Key decisions** | **Anonymous entry** so there's zero friction to start · **Mood tracking** that feels like a check-in, not a form · **Calm fallback states** that stay reassuring when the AI is slow or unavailable |
| **🎯 Outcome** | A gentle, anonymous-first experience that never leaves the user stuck or alone on a failed screen. |

<details>
<summary><b>🧠 See my design thinking</b></summary>

<br/>

- **Why anonymous first?** Asking someone to sign up before they feel better adds a reason to leave. Starting without an account lowers the emotional cost of the first step.
- **Why design the failure states?** In a well-being product, an abrupt error message at the wrong moment can feel like rejection. Fallbacks are written and designed to stay warm.
- **Why mood tracking as a check-in?** Short, low-effort input keeps the habit light and avoids "filling in a form" fatigue.

### 🧠 Quiz Buddy &nbsp;·&nbsp; Programming Practice Platform
<sub>Role: Product Design + Frontend &nbsp;|&nbsp; Tools: Figma, React, TypeScript</sub>

<p align="center">
  <img src="https://github.com/user-attachments/assets/ade75221-b57d-46d1-a8ce-72f7bc1ac6db" alt="Quiz Buddy preview" width="100%" />
</p>

| | |
|---|---|
| **🌸 Problem** | Practice tools are noisy, and learners get lost when loading, empty, or error states appear. |
| **💡 Approach** | Design the whole journey, including the unhappy paths, not just the ideal one. |
| **✨ Key decisions** | **Clear user flow** from topic → question → result → review · **Defensive UI states** for loading, empty and error · **Strong screen hierarchy** so feedback reads at a glance |
| **🎯 Outcome** | A focused practice flow where users always know where they are and what to do next. |

<details>
<summary><b>🧠 See my design thinking</b></summary>

<br/>

- **Why map the flow first?** A quiz is a loop. Getting the path from question to feedback to next action right matters more than any single screen.
- **Why defensive states?** Most products are only designed for the "everything works" case. Handling empty and failed states is where trust is built.
- **Why strict hierarchy?** Learners are concentrating on the question, so the interface should stay out of the way and make feedback unmistakable.

## 🧭 How I Work

<p align="center">
  <b>Understand</b> → <b>Map flows</b> → <b>Wireframe</b> → <b>Design in Figma</b> → <b>Build in React</b> → <b>Refine every state</b>
</p>

**Three principles I design by**

1. **Design for the worst moment.** Errors, empty screens and slow loads are part of the product, not an afterthought.
2. **Remove friction before adding features.** If a step doesn't help the user, it goes.
3. **Hierarchy first, decoration second.** Calm interfaces come from clear priorities, not from fewer elements.
